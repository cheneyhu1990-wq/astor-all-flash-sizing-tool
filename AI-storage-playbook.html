01 / 07Concepts

AI Fundamentals for Pre-Sales

Training, fine-tuning, inference, RAG, Agent, embeddings, checkpoints — get the vocabulary right before you get the opportunity right.

Why pre-sales must separate these concepts first

Most AI projects sound alike on the surface. A customer says they're "building a large model," "building a knowledge base," "building an Agent," or that "GPU utilization won't go up." Underneath, these can be completely different problems — and the fastest way to lose credibility on a call is to treat them as the same one.

"We're working on a large model" "We want to build a knowledge base" "We're building an Agent" "GPU utilization won't go up" "The model's answers aren't accurate" "Inference is too slow"

Without first separating these concepts, pre-sales tend to make three predictable mistakes: treating a training problem as an inference problem, treating a RAG/Agent problem as a model-training problem, and dressing up every AI application as a storage opportunity.

  • Mistake 1 — Mistaking a training-side problem for an inference-side problem.
  • Mistake 2 — Mistaking a RAG/Agent problem for a model-training problem.
  • Mistake 3 — Repackaging every AI application as a storage opportunity, regardless of evidence.

The correct sequenceFirst judge which stage of the AI project the customer is actually in. Only then judge whether a real data pressure exists.

What the customer says, and what's really going on

The same sentence can point to entirely different technical problems. Use this as a quick mental lookup the moment a customer says one of these.

Customer says

"We're working on a large model."

Ask firstIs this training, fine-tuning, or just calling a model API?

Only customers with a local GPU cluster, a steadily growing dataset, checkpoints, and multi-task concurrency are likely candidates for a training-side storage opportunity.

Customer says

"We want to build a knowledge base."

Judge firstThis is a RAG knowledge-data pipeline issue, not a model-training issue.

Focus on whether source documents, chunks, vectors, metadata, permissions, update records, and retrieval logs can be managed as one unified system.

Customer says

"We're building an Agent."

Judge firstAgent opportunities usually live in logs, permissions, tool calls, and feedback loops.

Many Agents are still demos. Whether a real opportunity exists depends on whether large-scale knowledge data, operating logs, and a genuine business closed loop already exist.

Customer says

"GPU utilization won't go up."

Locate firstThis looks more like a training-side data-loading problem.

Keep asking about the DataLoader, the training dataset, small-file counts, checkpoints, multi-task concurrency, and data movement between object, file, and cloud storage.

Customer says

"Inference is too slow."

Boundary reminderSlow ordinary inference doesn't mean AI Unified Storage can directly accelerate it.

Sangfor does not currently support KVCache / LMCache plugins. You can discuss the data management behind the inference app — logs, feedback data — but you cannot promise inference-cache acceleration.

Seven concepts every pre-sales rep must distinguish

If you can already tell these apart cleanly, skip ahead to Module 02. If not, this is the vocabulary the rest of the playbook assumes.

Training
What it is
Using large volumes of data so a model acquires a capability from scratch — text for language models, images for vision models, video and sensor data for autonomous driving, molecular and experimental data for AI drug discovery.
Typical data
Training samples, labels, data indexes, checkpoints, model weights, evaluation data.
Common pain points
GPU waiting on data, slow data loading, too many small files, scattered training data, slow checkpoint writes, chaotic dataset versions.
Pre-sales judgment
Focus on local GPU presence, dataset scale, multi-task concurrency, checkpoint frequency, and dataset version management.
Fine-tuning
What it is
Adapting an existing model using enterprise or industry-specific data — e.g. customer-service Q&A logs, medical literature and case data, financial research and trading data, robot operation data.
Typical data
Usually smaller scale than training from scratch, but far more dependent on high-quality, domain-specific data.
Common pain points
Whether enterprise data can be organized into training samples, data quality, version clarity, permission/compliance control, and whether results are reproducible.
Pre-sales judgment
Fine-tuning has real storage potential, but not every fine-tuning job needs large-scale, high-performance storage — small-scale fine-tuning may already run fine on existing infrastructure.
Inference
What it is
A model being called and returning a result — a user asks a question and the model answers, an image is classified, a customer-service system returns an answer, an autonomous-driving model makes a decision from sensor data.
What's in scope
Model-serving response speed, concurrency, inference cost, context handling, service stability.
Can discuss
The data management behind an inference app — the RAG/Agent knowledge-data foundation, log and feedback-data accumulation, raw data/vector/metadata/permission/lifecycle management.
Cannot discuss
Cannot claim to directly speed up all large-model inference, cannot claim KVCache/LMCache support, cannot claim to replace inference-serving frameworks.
RAG
What it is
Retrieval-Augmented Generation. The system first retrieves relevant content from an enterprise knowledge base, then hands that content to the large model, which generates an answer grounded in it.
Knowledge pipeline
Source documents → parsed text → chunks → vectors → metadata → permissions → update records → retrieval logs.
Where the opportunity sits
Source text and vectors managed separately, broken permission inheritance, vectors that drift out of sync after updates, document versions that can't be rolled back, fragmented knowledge sources across departments.
Pre-sales judgment
RAG is not training. Its core is not making the model relearn — it's making sure the model can reliably reference the enterprise's own knowledge.
Agent
What it is
A step beyond Q&A: an Agent doesn't just answer, it decomposes tasks, plans steps, calls tools, and executes actions — querying data and generating a report, working an enterprise ticketing system end-to-end, analyzing data and producing recommendations.
What it needs
Tool permissions, task orchestration, enterprise knowledge, operation logs, security audit trails, a feedback loop.
Where the opportunity sits
Tool-call logs, session data, the enterprise knowledge source itself, permissions and audit, feedback data flowing back in, a traceable data foundation.
Pre-sales judgment
Agent sounds advanced, but many customers are still at demo or pilot stage. A real opportunity requires scaled knowledge data, operating logs, and an actual business closed loop.
Embedding & Vectors
What it is
Converting text, images, or other content into a set of numbers — vectors — so a system can search by meaning rather than by keyword. A query about "travel reimbursement standards" can match the semantically relevant policy section even without that exact phrase.
The catch
A vector is not a complete knowledge base. A usable enterprise knowledge base also needs the source document, chunks, metadata, permissions, version, lifecycle, and an update mechanism.
The correct framing
Raw data and vector feature data stored at the same source, under one lifecycle, with joint query support.
Cannot discuss
A Vector Bucket is not a complete RAG platform, does not replace the entire vector-database ecosystem, and does not by itself fix every knowledge-base accuracy problem.
Checkpoint
What it is
The saved model state during training, including model weights, optimizer state, and training configuration — captured periodically so a long-running job can recover without restarting from zero.
Why it matters
Supports fault recovery, staged saves, model rollback, and comparison across different experiment branches.
Storage characteristics
Files are usually large, writes are periodic, stability requirements are high, and read performance during recovery matters just as much as write performance.
Pre-sales judgment
A checkpoint is a recoverable state during training — it directly determines how much is lost when a training job fails.

02 / 07Framework

AI Storage Scenario Overview: Locate the Pressure First

Before you talk product, build the first-layer qualification framework — find where the customer's data is under real, sustained pressure, and whether Sangfor can honestly meet it.

The right first question is never "how big is your dataset?"

When a customer says they're "doing AI," pre-sales can't default to assuming a storage opportunity. Three questions must come first:

  1. Where exactly does the customer's data pressure occur?
  2. Is that pressure genuine, sustained, and operating at scale?
  3. Can Sangfor AI Unified Storage address it within its honest capability boundary?

An AI storage opportunity doesn't come from "the customer uses AI." It comes from the data lifecycle behind an AI project developing a real conflict — in performance, governance, versioning, permissions, data mobility, or reliability.

Core mental modelEvery AI project, on the surface, is about models, GPUs, applications, and algorithms. Underneath, it's a continuously running data supply chain. Follow the chain to find the real pressure point.

The full data supply chain behind any AI project

When qualifying an opportunity, don't start with "how large is your model?" or "what's your capacity requirement?" These more diagnostic questions are more productive:

About the data itself:

  • Where does the data come from?
  • What processing stages does it go through?
  • Which teams are using it?
  • How often is it updated?
  • Is the current bottleneck performance, governance, versioning, permissions, or cross-system mobility?

About the business impact:

  • Does this problem affect GPU utilization?
  • Does it hurt knowledge-base accuracy?
  • Does it slow down R&D velocity?
  • Does it delay business go-live windows?
Full data lifecycle — 10 stages:
  • Data collection → Cleaning → Labeling → Dataset management
  • Training or fine-tuning → Checkpoint / model-weight storage
  • Model evaluation and experiment tracking → Model or knowledge-base release
  • RAG/Agent retrieval and invocation → Inference logs, user feedback, data backflow

Three types of data pressure that create storage opportunities

1 — Training / Fine-Tuning: GPU data-supply pressure

The fundamental challenge is keeping GPUs fed. Once a customer has invested in GPU clusters, a training framework, and an algorithm team, expensive GPUs will sit idle if the data-loading pipeline can't keep up.

Typical signals:

  • A local GPU cluster or intelligent-computing platform
  • Ongoing training or fine-tuning workloads
  • Steadily growing dataset (small files, images, video, text, sensor data mixed)
  • Slow training startup; GPU utilization not reaching target
  • Checkpoint writes disrupting training cadence
  • Multiple teams sharing a dataset, with version and permission chaos

Corresponding storage needs:

  • High-bandwidth data reads
  • Low-latency small-file access
  • High-concurrency metadata operations
  • Stable checkpoint writes with fast recovery
  • Dataset version management
  • Hot/warm/cold lifecycle tiering
  • Data mobility between file, object, and cloud storage
2 — RAG / Agent: Knowledge data governance pressure

The core challenge is not "can we call a large model?" — it's whether the enterprise's knowledge can be retrieved correctly, promptly, and safely.

Typical signals:

  • A private knowledge base under construction
  • Documents scattered across multiple systems, departments, or storage environments
  • Need to link source documents, chunks, vectors, metadata, and permissions
  • Frequent knowledge updates but unclear vector-sync mechanism
  • Permissions exist in the source system but are lost when documents enter the knowledge base
  • Knowledge-base errors that need rollback
  • Agent operation logs and feedback data that need to accumulate somewhere

Corresponding storage needs:

  • Source data and vectors stored at the same origin
  • Metadata and permission association
  • Knowledge version control
  • Lifecycle management
  • Unified view across multiple sources
  • Joint query capability
  • Log and feedback data accumulation

Boundary reminder: Sangfor can discuss the RAG/Agent knowledge-data foundation. A Vector Bucket is not a complete RAG platform, and Sangfor capability cannot be packaged as KVCache/LMCache inference-cache acceleration.

3 — Industry AI: Data closed-loop pressure

Industry AI isn't a one-shot training job or a single knowledge base — it's a system that continuously produces data, uses data, feeds data back, and then re-optimizes models or business systems. The shared characteristic across verticals is continuous data movement with compounding value.

Typical scenarios:

  • Autonomous driving: collect → label → train → simulate → backfeed
  • Embodied AI: real-world data + simulation data + robot logs + training loop
  • AI drug discovery: molecules, proteins, experiments, literature, AI4S training, research knowledge base
  • Quant funds: market data, order book, factors, backtesting, strategy versions, researcher collaboration

Corresponding storage needs:

  • Multimodal data management
  • Large-scale dataset organization
  • Traceable experiments and versions
  • Multi-team collaborative access
  • Data lifecycle and archiving
  • Cross-system data mobility
  • Feedback data backflow

Qualifying the opportunity level

Strong opportunity
  • GPU cluster, intelligent-computing platform, or training platform in place
  • Steadily growing dataset
  • High-value data: multimodal, scientific, autonomous driving, robotics, financial
  • A training/fine-tuning/evaluation/data-backflow loop exists
  • A private knowledge base, RAG/Agent, or enterprise knowledge governance need
  • Data fragmented across file, object, cloud, or third-party storage
  • Active pain: GPU waiting on data, knowledge updates failing, permission chaos, versions out of control, cross-system migration is painful
  • Budget may fall to IT, data platform, AI platform, or infrastructure team
Recommended action: Advance to customer discovery, initial technical validation, and solution alignment conversations.
Developing opportunity
  • AI project exists but data scale, GPU scale, or budget isn't clear yet
  • A private knowledge base is planned but still in pilot
  • Industry data assets exist but no continuous training loop yet
  • Existing NAS, object storage, or data lake, but pain points not quantified
  • Boundary between AI team and IT team responsibility is unclear
Recommended action: Don't rush a full proposal. Do customer discovery and requirements investigation first; confirm data scale, business pressure, and budget ownership.
Weak or false opportunity
  • Only calling external large-model APIs
  • No local data assets
  • No GPU cluster or training workloads
  • No private knowledge base
  • Data scale is small; the existing environment is sufficient
  • AI application is just a front-end feature wrapper
  • Budget is mainly in application development, not infrastructure
  • Customer pain is about model accuracy, prompts, and application flow — not data and storage
Recommended action: Don't force-fit it into an AI Unified Storage opportunity. A professional pre-sales rep de-qualifies cleanly to protect scarce team resources.
Initial diagnostic questions by direction

Training / Fine-tuning

  • Is there a local GPU cluster or intelligent-computing platform?
  • What's the current dataset scale, file types, and count?
  • Is GPU utilization being impacted by data loading?
  • How often are checkpoints written; how's recovery when things fail?

RAG / Agent

  • What are the knowledge sources — documents, databases, business systems, web pages?
  • How are source docs, chunks, vectors, and metadata managed today?
  • Do permissions need to be inherited from the source system?
  • How often is knowledge updated; does the vector sync?

Industry data loop

  • Is data produced continuously or imported once?
  • Does data flow across multiple systems, teams, or locations?
  • Does data need long-term retention, traceability, or version comparison?

03 / 07Software Ecosystem

The AI Software Ecosystem: Don't Just Watch the Model

Customers talk in GPU clusters, PyTorch, K8s, vector stores, LangChain, MLOps. Pre-sales who only hear "model" miss the real problem. Understand the three-layer stack and you can translate any technical environment into a data-chain question.

The three-layer AI software stack

When a customer talks about AI, they're likely mixing terms from three distinct layers. These layers interact, but they are not the same system — and a problem in one layer cannot be solved by the tools in another.

Layer 1 — Training / Fine-Tuning Stack

Makes the model acquire or adapt a capability. Includes: GPU cluster → CUDA/NCCL → PyTorch/TensorFlow → DataLoader → Slurm/K8s scheduler → File / Object / Data Lake storage.

Layer 2 — RAG / Agent Application Stack

Lets the model apply enterprise knowledge and tools to complete tasks. Includes: Document parsing → Chunking → Embedding and vector search → RAG frameworks → Agent frameworks → Permissions and audit.

Layer 3 — Data & Platform Foundation

Supports data, permissions, scheduling, storage, and lifecycle across both layers. Includes: MLOps / LLMOps → Metadata systems → Permission and audit → Multi-protocol and multi-source data management. This is where Sangfor AI Unified Storage lives.

Layer 1 deep-dive: Training / Fine-Tuning Stack

Think of the training side as a coordinated system: GPU + framework + data-loading + scheduling + storage. Any component in that chain can starve the others.

GPU ClusterCore resource

Once a customer has invested in GPUs, the worst outcome is those GPUs waiting — not for compute, but for data, scheduling, or checkpoint writes. Watch for scale (count and model), single-node vs. multi-node multi-GPU, training job duration, and GPU utilization stability.

AskIs there a data-loading bottleneck? Are training tasks long-running? What's the consistent GPU utilization rate?
CUDA / NCCLFoundation layer

CUDA is NVIDIA's GPU-compute foundation. NCCL handles communication across multiple GPUs and nodes. Pre-sales doesn't need the implementation details — but when a customer says "multi-node multi-GPU efficiency won't come up," don't immediately assume it's a storage problem. It could be communication, scheduling, data loading, framework configuration, or checkpoint writes.

AskWhat specifically is happening when efficiency drops? Have you ruled out network and scheduling?
PyTorch / TensorFlowTraining framework

These are the frameworks algorithm engineers write training code in. Storage-related problems show up as: slow data preparation before training begins, DataLoader reads that can't keep up, random-read pressure from many small-file samples, metadata pressure from multi-process reads, and checkpoint writes interrupting the training rhythm.

AskAre you seeing slowdowns before training starts, mid-training, or both? What's the DataLoader worker count?
DataLoaderCritical pipeline

DataLoader is the pipe feeding data into the model. If it's slow, GPUs wait. The symptom is low GPU utilization — but the root cause could be data organization, storage performance, network path, preprocessing logic, or small-file count. Always dig into the root cause.

AskLarge files or small files? Sequential reads or random? How many workers per training task? Is real-time decoding or augmentation happening at read time? Reading from filesystem, object storage, or local disk?
Slurm / K8s / Training PlatformsScheduler / orchestrator

Scheduling systems amplify storage pressure. Multiple training tasks starting simultaneously can cause sudden mass-reads of config, samples, and dependency files. Multiple tasks writing checkpoints simultaneously creates burst-write pressure.

AskAre tasks launched in bursts? Multiple teams sharing the cluster? Is there a unified dataset directory? Is there task-level data isolation and permission separation?
File / Object / Data Lake StorageData substrate

Training data typically spans file systems, object stores, data lakes, and cloud storage simultaneously. This fragmentation produces real problems: data copying overhead, protocol fragmentation, permission inconsistency, and scattered lifecycle policies. Sangfor can address the co-existence and mobility problem across these substrates.

AskWhere exactly does the training data live today? Has the team needed to copy data between systems? Is there a single access path, or multiple?

Layer 2 deep-dive: RAG / Agent Application Stack

The RAG/Agent side is not a simple extension of the training stack. Think of it as: knowledge data + retrieval + large model + application orchestration + permission governance.

Document ParsingIngestion layer

Enterprise knowledge lives in PDFs, Word docs, PPTs, web pages, policy documents, technical manuals, tickets, databases, and business systems. Parsing converts these into text or structured content the model can process. Storage's entry point: source documents, parsed results, metadata, and versions must be managed together — you can't keep only the vectors.

AskWhat format are the source documents in? Are there complex tables, images, or scanned documents? Is the original source traceable?
ChunkingRAG pipeline step

Long documents are split into smaller segments before being vectorized and retrieved. Chunk quality affects answer accuracy, but chunking itself is not a storage capability. Storage's concern: are chunks linked to their source document? Do chunks carry version numbers? Do they inherit the source's permissions? Are they updated when the document changes?

Embedding & Vector SearchRetrieval engine

Vectors enable semantic search. But "customer has vectors" doesn't automatically mean they need a Vector Bucket. Ask: Is there a source/vector split problem? Is unified lifecycle needed? Is joint query of source, vector, and metadata needed? Do permissions and versions need managing? The Vector Bucket entry point is the data foundation — not the complete RAG application platform.

AskAre source documents and vectors managed in separate systems? When a document changes, does the vector automatically update? Can you search across source text and vector data together?
RAG Frameworks (LangChain, LlamaIndex, Dify, etc.)Application-orchestration layer

RAG frameworks handle retrieval, context assembly, and model generation. These live at the application-orchestration layer — they are not equivalent to underlying data governance. When a customer says "RAG answers aren't accurate," the cause could be document quality, parsing errors, poor chunking strategy, the wrong embedding model, incorrect permission filtering, stale knowledge, or retrieval-ranking problems. Don't immediately attribute inaccuracy to storage — but do check whether source/vector/metadata/permission/version fragmentation is the underlying issue.

Agent FrameworksTask execution layer

Agent frameworks enable models to decompose tasks, call tools, and execute multi-step workflows — calling search tools, databases, enterprise systems, reporting platforms, ticket systems, and code/script tools. All of this generates data: session records, tool-call logs, execution results, permission records, error logs, user feedback. When these data streams enter a feedback loop, a new data-governance and storage opportunity forms.

AskIs the Agent calling enterprise systems? Are those tool calls audited? Where do logs go? Does feedback data flow back to improve the knowledge base?
Permission SystemsGovernance layer

Permissions are frequently the blocker that prevents enterprise AI from moving to production. Customers worry about: who can see the source document, whether permissions are still valid once documents enter the knowledge base, whether vector retrieval can accidentally surface unauthorized content, whether Agent tool calls are audited, and whether permissions stay in sync after personnel changes. Storage can't replace a full IAM system — but it can help customers reduce the risk of knowledge-data becoming ungoverned, by managing source, vector, metadata, version, and lifecycle together.

Layer 3 deep-dive: Data & Platform Foundation

MLOps / LLMOps PlatformsPlatform layer

MLOps covers model training, experiment management, deployment, and monitoring. LLMOps extends to large-model application lifecycle management: prompts, evaluation, RAG, Agent. These platforms depend on storage — but they are not storage itself. Entry points: dataset management, model-weight management, checkpoint management, experiment traceability, knowledge-base source and vector management, log and feedback accumulation.

Metadata SystemsData intelligence layer

As AI projects mature, metadata becomes increasingly critical — data origin, collection time, labeling status, data version, permission tags, model version, experiment parameters, evaluation results, knowledge-update timestamps. Without metadata, the larger the data scale, the harder it is to govern. Think of metadata as the AI data asset's "documentation and index system."

Multi-Protocol & Multi-Source DataConnectivity layer

Customer data typically lives across NFS directories, SMB shares, S3 buckets, third-party file/object storage, cloud storage, data lakes, and business systems simultaneously. This fragmentation produces copying overhead, redundant storage, permission inconsistency, and version divergence. Sangfor's data mobility, heterogeneous-source management, unified view, and protocol interoperability capabilities are specifically positioned to address this layer.

AskDoes the AI team need to copy data between systems to use it? Has the same dataset been stored in multiple places? Are there permission or version inconsistencies between systems?

Module 03 — Takeaway

The AI software ecosystem is not captured by any single model. Training side: look at GPU, framework, data loading, scheduling, and storage as a coordinated system. RAG/Agent side: look at document parsing, vectors, retrieval, permissions, tool calls, and knowledge-data governance. Platform side: look at datasets, metadata, permissions, versions, protocols, and lifecycle. Pre-sales don't need to become algorithm engineers. 04 / 07Data Anatomy

AI Data Is Not One Thing

Training data, model data, and knowledge data are three fundamentally different categories. Learn each type's I/O profile and you stop over-relying on "high capacity, high bandwidth" as the only answer.

The single most important shift in how you think about AI storage

Too many pre-sales conversations stall at "volume is large, bandwidth is high." That's not wrong — it's just incomplete. AI projects carry radically different data types, each with its own access pattern, lifecycle, permission profile, and business value. Unless you pull those apart, your solution will always be a parameters dump.

The correct reasoning chain: Data type → Data characteristics → I/O profile → Customer pain point → Storage requirement.

Three major data categories — never conflate them

Training Data

Supports model learning or fine-tuning. Focus on the efficiency of the GPU-to-data supply path. Examples: text corpora, labeled images, video clips, sensor streams, molecular samples.

Model Data

Records model state, weights, and the experimental process. Focus on checkpoints, weights, versions, and recovery. Examples: checkpoint files, model weights, evaluation metrics, experiment configs.

Knowledge Data

Each data type, in full detail

Raw Data — the upstream source for everything

Text (documents, contracts, policy, research reports, work orders), images (medical imaging, industrial vision, robotics vision), video (autonomous-driving footage, embodied-AI training clips), audio (call-center recordings, meeting audio), sensor data (LiDAR, millimeter-wave radar, IMU, robot state), experimental data (molecules, proteins, simulation results, lab records), financial data (market data, order books, factors, backtesting inputs).

Pre-sales caution: Large raw-data volume does not automatically mean a high-performance storage opportunity. The critical question is whether the data is continuously being used for training, retrieval, evaluation, or backflow — not just stored.

Training Samples & Labels — from raw data to trainable format

What training samples include: cleaned text corpora, labeled images and video, autonomous-driving scene clips, robot operation trajectories, molecular structures with experimental labels, financial factor samples.

What labels include: classification labels, bounding boxes, segmentation masks, behavioral trajectories, Q&A pairs, preference or rating data.

Characteristics: large file counts, high proportion of small files, frequent version changes, lineage relationships with raw data, shared and repeatedly reused across teams.

Storage requirements: small-file low latency, metadata performance, dataset version management, permission isolation, data lineage and traceability, multi-team shared access.

Note: Customers with a labeling platform, a dataset management platform, or a multi-team reuse mechanism are typically stronger opportunities.

Checkpoints & Model Weights — critical training-state data

Characteristics: files are typically large; writes are periodic; read/write peaks are pronounced; when multiple experiments run in parallel, versioning becomes complex; recovery and rollback dependencies are strong.

Pain points: checkpoint writes slow down training, multi-task concurrent writes cause jitter, recovery is slow after a failed run, model weight versions become confused, experiment results and model files are hard to correlate.

Storage requirements: stable large-file writes, high-bandwidth reads, version control, fast recovery, experiment-to-model-file linkage, reliability and protection against accidental deletion.

Pre-sales: Checkpoints are one of the strongest training-side entry points. The longer the training runs, the larger the model, and the more experiments there are, the higher the value of checkpoint management and recovery.

Evaluation Data & Experiment Results — the gate to production

Evaluation data includes: test sets, validation sets, benchmarks, domain-specific evaluation samples, and human-review results.

Experiment results include: metric outputs, parameter configurations, training logs, model versions, dataset versions, and comparison reports.

Characteristics: individual data volumes may be smaller, but management complexity is high — strong dependence on versioning and reproducibility; multiple experiments, branches, and models running in parallel; long-term retention and comparison required.

Note: For AI pharma, quant funds, autonomous driving, and scientific research, experimental reproducibility and result traceability are often non-negotiable gating criteria.

RAG Knowledge Data — source, chunks, vectors, and metadata must be seen together

The complete RAG data chain:

  1. Source document
  2. Parsed document text
  3. Document chunks
  4. Embedding vectors
  5. Metadata
  6. Permission information
  7. Version records
  8. Retrieval logs

Why they must be managed together:

  • Source text and vectors have a mapping relationship
  • Document updates affect both chunks and vectors
  • Permissions must be inherited or re-bound
  • Metadata controls retrieval filtering and governance quality
  • Lifecycle can't manage just vectors and ignore the source
RAG storage opportunity: enter from knowledge-data governance, not "model inference acceleration." A Vector Bucket should be described as co-located source and vector management — never as a complete RAG platform.
Agent Runtime Data — new data streams from execution

What Agent execution generates: session records, task plans, tool-call logs, data-query records, execution results, error records, user feedback, audit information.

Characteristics: data is produced continuously, strongly linked to permissions/audit/business processes, may need long-term retention, and serves as raw material for subsequent optimization and risk control.

Storage requirements: log accumulation, audit traceability, permission association, feedback-data backflow, lifecycle management, linkage with the knowledge base and business system data.

Pre-sales: The Agent storage opportunity is not the model itself — it's runtime data, permission auditing, knowledge-source management, and a feedback loop. Many Agent projects are still in pilot; verify whether scaled runtime data actually exists.

Every AI storage qualification conversation should move through these five stages — not necessarily in a single meeting, but in this sequence.

01Stage 1 — Establish the AI project stage

Don't dive into storage requirements before you know where in the AI lifecycle the customer actually sits. Ask a few simple questions to locate them on the pipeline.

Locating questions
  1. What phase is the AI project currently in — model training, fine-tuning, deploying an inference service, building a knowledge base, or developing an Agent?
  2. Are you training or fine-tuning models yourselves, or calling an external large-model API?
  3. Do you have a local GPU cluster or intelligent-computing platform?
  4. Is your knowledge base proprietary, or are you using a third-party service?
What to listen for
  1. Local compute → likely training/fine-tuning opportunity
  2. Private knowledge base → likely RAG/Agent opportunity
  3. External API only, no local data → downgrade immediately
  4. Industry-specific data loop → go deeper on the data closed-loop questions
02Stage 2 — Map the data supply chain

Once you've established the project stage, follow the data. Ask where it comes from, how it moves, where it lives now, and where the friction is.

Training / fine-tuning questions:

  • What types of data does your training dataset contain — images, video, text, audio, sensor data?
  • Roughly how many files and what's the total size?
  • Is GPU utilization hitting the level you'd expect?
  • How does data loading work — does the DataLoader ever become a bottleneck?
  • How often are checkpoints written, and how large are they?
  • When a training job fails, how long does recovery take?
  • How many teams share the training dataset, and how do you manage versions?
  • Where does the training data physically live — NFS, object storage, local disk, cloud?

RAG / Agent questions:

  • What are the sources for your knowledge base — internal documents, databases, web pages, business systems?
  • Where do source documents, chunks, vectors, and metadata live today — are they in separate systems?
  • When a source document is updated, how do the vectors get re-synchronized?
  • Do retrieval permissions need to match the original document's access controls?
  • Have you ever needed to roll back a knowledge-base update?
  • Where do Agent tool calls, session logs, and user feedback go?
03Stage 3 — Surface and validate the pain

It is not sufficient for a customer to mention a problem in passing. You need to establish that the pain is real, sustained, and creating a measurable business consequence — otherwise there is no budget driver.

Pain confirmed — pursue
  • Customer can name the specific bottleneck and quantify its impact
  • GPU utilization drop is measurable and consistent
  • Training recovery after failure takes hours or days
  • Knowledge-base errors caused a real business incident
  • Data migration between systems is slowing a release schedule
  • A dataset version conflict forced a reproducibility failure
  • Budget conversation has already started
Pain suspected — dig deeper
  • Customer mentions it vaguely but can't quantify
  • Team is aware of the issue but has been "living with it"
  • No one owns the problem yet
  • A solution exists but it's manual and fragile
  • The issue surfaces only at peak load or scale
Action: Ask follow-up questions to help the customer quantify the impact. If they can put a number to the cost — GPU idle time, lost experiments, delayed releases — the conversation becomes much easier.
Script example — surfacing the checkpoint pain

"When a training job fails mid-run, roughly how long does it take to get back to where you were? And when multiple jobs are writing checkpoints at the same time, do you notice any impact on the training rhythm of the other jobs?"

Once pain is confirmed, map it to a specific Sangfor capability. Use the guardrail from Module 06 on every claim: can say now, must label as upcoming, or must never say.

05Stage 5 — Make the qualification call

After the conversation, make an explicit judgment. Don't leave the opportunity in an ambiguous state. Pre-sales resources are finite — the fastest path to a closed deal is a clean qualification or a clean downgrade.

Advance — qualify and proceed
  • Pain is confirmed and quantified
  • Sangfor can address it with available or roadmap capability
  • Budget conversation is underway or owner is identified
  • The data scale and complexity justify an enterprise storage solution
  • Decision timeline is visible
Next step: Engage solution architect for technical validation. Scope a PoC or reference architecture. Get the customer's full data environment mapped.
Downgrade — exit cleanly
  • Only calling an external API — no local data assets
  • No GPU cluster, no training workloads
  • Pain is vague, unquantified, and unowned
  • Budget is locked in application development
  • Problem is in model accuracy, prompts, or application flow — not data and storage
  • Existing infrastructure is adequate for current scale
Remember: A clean downgrade protects your credibility and frees your time for winnable opportunities. It is professional, not a failure.

The three most common on-site presentation mistakes

Mistake 1 — Leading with parameters instead of problems

What it looks like: Opening the meeting with bandwidth numbers, IOPS figures, capacity specs, and protocol support lists before the customer has described a single pain point. The customer nods politely and asks "so what problem does this solve for us?" and you've lost the room.

The fix: Every technical parameter in the presentation must be preceded by the customer problem it addresses. Lead with the scenario, then the pain, then the capability, then the spec.

Instead of

"Our single-node read bandwidth reaches 120 Gbps..."

Say instead

"When your autonomous driving training tasks start reading several terabytes of video and LiDAR data concurrently, the storage needs to keep up with those GPUs. At 120 Gbps read per node, we can..."

Mistake 2 — Conflating roadmap capabilities with available ones

What it looks like: Discussing Vector Bucket, Unified Data View, Dataset Version Control, S3 over RDMA, and NVIDIA cuObject as if they are available today — or worse, letting a customer sign a contract based on an implied GA date that hasn't been confirmed. This is the fastest way to damage both your personal credibility and Sangfor's market position.

The fix: Establish a two-tier system in every deck and verbal presentation. Available now gets a solid checkmark. Roadmap / upcoming gets an explicit label — spoken aloud, not buried in a footnote.

Script for roadmap capability

"This is a roadmap capability we're calling Vector Bucket — I want to be transparent that it is not yet generally available. Our current timeline positions it for the upcoming release. I'm happy to share a technical preview brief, but we'd plan any commercial commitments around what's shipped today."

Mistake 3 — Dressing up every AI use case as a storage opportunity

What it looks like: The customer mentions they're building a chatbot or deploying a customer-service AI. You immediately pivot to AI Unified Storage without first checking whether they have any local data, GPU resources, or knowledge-governance needs. You spend 45 minutes on a proposal for a customer who is simply calling an external API.

The fix: The ten pre-meeting questions from Module 04, and the five-stage qualification structure in this module, exist precisely to prevent this. The signal check from Module 02 — is there a GPU cluster? Is there local data? Is there a private knowledge base? — takes less than five minutes to run.

Remember: A clear de-qualification in the first meeting is more valuable than a proposal you'll never close. It protects your credibility and positions you as the pre-sales rep who doesn't waste the customer's time.

How to handle the four most common difficult questions

"Can your storage directly accelerate large-model inference?"

Why it's a trap: This question is asking about KVCache / LMCache inference-serving optimization — which is not what Sangfor AI Unified Storage does. Saying "yes" to get through the objection will create a credibility problem when the customer evaluates the solution in a PoC or production environment.

Recommended response

"For inference-serving speed, the critical factors are model serving frameworks, GPU resources, and concurrency architecture — those sit above the storage layer. What we can address is the data management behind the inference application: the knowledge-base source and vectors that power a RAG/Agent system, the logs and feedback data generated during inference, and the training-data supply chain that keeps the model updated. If the performance problem is specifically about serving latency and GPU utilization in inference, we'd want to engage your infrastructure and algorithm teams together to find the right root cause."

"Does your Vector Bucket replace our existing vector database?"

Why it's a trap: Claiming Vector Bucket replaces a dedicated vector database (Milvus, Weaviate, Chroma, Pinecone) overstates what it does and creates a false competitive frame. Vector Bucket's value is at the data-governance and co-location layer — not as a full-featured vector database engine.

Recommended response

"Vector Bucket isn't positioned to replace your vector database engine — it's designed to solve the problem that comes before that: keeping source documents and their corresponding vectors in sync, under a shared lifecycle, with consistent permissions. Today many teams store source text in a file share, vectors in a separate vector DB, metadata in a database, and permissions in yet another system — and when a document changes, those four systems drift apart. Vector Bucket addresses that governance problem. I also want to be clear: this is an upcoming capability, not yet generally available."

"We're using an external large-model API. Do we still have a storage need?"

The correct answer is often "no" — but verify before you conclude. External API usage means no local training. But the customer may still have a private knowledge base, internal documents to govern, permission requirements, or a pipeline of internal data flowing into the API.

Recommended response

"If you're purely calling an external API with no local data assets or private knowledge base, then honestly, that's a weak fit for AI Unified Storage right now. But I'd want to ask one more question: do you have any internal documents, proprietary data, or a knowledge base you're managing to feed that API? If permissions, version control, or knowledge governance are becoming complex, that's where a different kind of conversation starts."

"How does Sangfor compare to [competitor] on AI storage?"

Be precise before you compare. The first question is always: what specific capability is the customer comparing? AI storage is a broad category. A comparison on training-data throughput is a different conversation from one on RAG knowledge governance or data mobility. Don't make a blanket competitive claim.

Recommended response

"Before I compare, I want to make sure we're comparing the right things. Are you evaluating us on training-data throughput for a GPU cluster? Knowledge-data governance for a RAG pipeline? Multi-source data management and lifecycle tiering? Each of those is a different dimension, and our positioning varies by scenario. What's the specific use case you're benchmarking against?"

The single most important principle

The core professional standardEvery AI project discussion should be brought back to the data lifecycle. Module 07 — Final Takeaway

The field playbook is simple: Place → Press-test → Match. Every call starts by placing the customer on the AI data lifecycle. Every conversation tests whether the pressure is real and at scale. Every solution maps to a specific capability — with absolute honesty about what is shipped, what is upcoming, and what is outside Sangfor's scope today. Pre-sales credibility is built by saying less and meaning more. Know the boundary. Respect it. That is what earns a seat in the customer's architecture conversation.
